# SQLite vs MySQL vs PostgreSQL 选型对比

> 针对 `radio-association` 项目（协会信息展示与招新管理系统）的后端数据库选型分析。

---

## 1. 项目特征

| 维度 | 现状 |
|------|------|
| 数据规模 | 小：协会信息、部门、竞赛、培训、荣誉为静态数据；报名信息每年新增数百至数千条 |
| 并发量 | 低：主要在招新季节有访问高峰，日常访问量很小 |
| 写入频率 | 低：主要是管理员录入/修改静态数据 + 学生提交报名 |
| 事务复杂度 | 低：无复杂事务、无多表 JOIN、无高并发库存/计数场景 |
| 部署环境 | 单机/小型 VPS，Bun + Express 后端 |
| 运维能力 |  likely 由协会学生维护，倾向于简单、零运维 |

---

## 2. 三种数据库对比

### 2.1 功能适配

| 维度 | SQLite | MySQL | PostgreSQL |
|------|--------|-------|------------|
| 数据存储方式 | 单文件 (`database.sqlite`) | 独立服务端进程 | 独立服务端进程 |
| SQL 兼容性 | 基本兼容，功能子集 | 广泛支持，生态成熟 | 标准 SQL 最完整，JSON 支持强 |
| 并发写入 | 单文件写锁，写并发弱 | 强 | 强 |
| JSON 支持 | 需手动序列化/解析 | 有 JSON 类型但一般 | 原生 JSONB，支持索引和查询 |
| 连接方式 | 本地文件直接访问 | TCP/Unix Socket | TCP/Unix Socket |
| 备份方式 | 复制文件即可 | mysqldump / 物理备份 | pg_dump / 物理备份 / WAL 归档 |

**本项目结论**：功能需求简单，三种数据库都能满足。PostgreSQL 的 JSON 能力在本项目属于“锦上添花”，非必需。

---

### 2.2 开发难度

| 维度 | SQLite | MySQL | PostgreSQL |
|------|--------|-------|------------|
| 安装依赖 | 已内置于 Bun（`bun:sqlite`） | 需安装 MySQL Server 或 Docker | 需安装 PostgreSQL Server 或 Docker |
| 驱动配置 | 零配置，直接 `require('bun:sqlite')` | 需安装 `mysql2` 等驱动，配置连接池 | 需安装 `pg` 驱动，配置连接池 |
| 代码改动量 | 当前实现即为 SQLite | 中等：需替换 `bun:sqlite` 为 `mysql2`，SQL 语句基本兼容 | 较大：需替换为 `pg`，连接池/参数化风格不同，部分 SQL 语法需调整 |
| 同步/异步 | 当前 `bun:sqlite` 为同步，代码简洁 | 必须异步，路由需 `await` 所有查询 | 必须异步，路由需 `await` 所有查询 |
| 本地开发 | 删除 `server/data/database.sqlite` 即可重置 | 需启动/停止服务，管理数据库和用户 | 需启动/停止服务，管理数据库和用户 |
| 多环境一致性 | 高：文件即数据库 | 中：需保证本地/测试/生产环境一致 | 中：需保证本地/测试/生产环境一致 |

**本项目结论**：SQLite 开发成本最低，与现有代码无缝契合。切换至 MySQL/PostgreSQL 会引入连接池、异步驱动、环境管理等问题，对小型项目属于过度设计。

---

### 2.3 运维难度

| 维度 | SQLite | MySQL | PostgreSQL |
|------|--------|-------|------------|
| 部署成本 | 极低：无需单独安装数据库服务 | 中：需安装并配置 MySQL 服务 | 中：需安装并配置 PostgreSQL 服务 |
| 监控需求 | 低：文件大小、磁盘空间 | 中：连接数、慢查询、内存、复制状态 | 中：连接数、WAL、 vacuum、复制状态 |
| 备份恢复 | 极简单：复制文件或使用 `bun:sqlite` 备份 | 中等：mysqldump + 定时任务 | 中等：pg_dump + 定时任务 |
| 故障恢复 | 简单：恢复文件即可 | 较复杂：binlog 恢复、主从切换 | 较复杂：WAL 归档、PITR |
| 权限管理 | 无：依赖文件系统权限 | 有：用户、库、表级权限 | 有：角色、Schema、行级安全策略 |
| 扩展（分库分表） | 弱 | 强 | 强 |

**本项目结论**：SQLite 对“学生协会、单实例、低并发”场景最友好。MySQL/PostgreSQL 的运维能力在此项目中无法体现价值，反而增加维护负担。

---

## 3. 综合评分（5 分制）

| 维度 | SQLite | MySQL | PostgreSQL |
|------|--------|-------|------------|
| 功能适配 | 4 | 5 | 5 |
| 开发简单 | 5 | 3 | 2 |
| 运维简单 | 5 | 3 | 2 |
| 与本项目代码契合 | 5 | 2 | 1 |
| 未来扩展性 | 2 | 4 | 5 |
| **综合推荐度** | **5** | 3 | 2 |

---

## 4. 推荐方案

### 当前阶段：继续使用 SQLite

理由：
- 项目规模小、并发低，SQLite 完全胜任。
- 与现有 `bun:sqlite` 代码无缝集成，无需改动。
- 开发和运维成本最低，适合学生协会长期维护。
- 备份简单：只需定期复制 `server/data/database.sqlite`。

### 可考虑迁移的时机

若未来出现以下情况，再考虑迁移：
- 并发访问量显著增长（如同时数百人提交报名）。
- 需要多应用实例部署（负载均衡）。
- 需要复杂的数据分析、全文搜索、GIS 等高级功能。
- 需要多人在线管理后台并频繁并发写入。

### 如果一定要迁移，建议顺序

```
SQLite → MySQL → PostgreSQL
```

- **MySQL**：迁移成本低于 PostgreSQL，社区资料多，运维相对简单。
- **PostgreSQL**：功能最强，但迁移和运维成本最高，适合有专职运维团队的项目。

---

## 5. 给本项目的 SQLite 优化建议

即使继续使用 SQLite，也建议做以下改进：

1. **定期备份**：
   ```bash
   cp server/data/database.sqlite server/data/database.sqlite.backup.$(date +%Y%m%d)
   ```

2. **启用 WAL 模式**：已启用（`server/config/database.js`）。

3. **避免长时间事务**：当前写入简单，基本无问题。

4. **数据库文件权限**：确保 `server/data/database.sqlite` 的读写权限正确，避免部署后因权限不足报错。

5. **数据迁移脚本**：如果未来需要迁移，先写好 `initDB.js` 的等价脚本和目标数据库 schema，降低迁移风险。

---

## 6. 结论

| 数据库 | 是否推荐本项目 | 原因 |
|--------|---------------|------|
| SQLite | ✅ 强烈推荐 | 零配置、低运维、与现有代码完全契合 |
| MySQL | ⚠️ 不推荐当前使用 | 引入额外运维复杂度，功能冗余 |
| PostgreSQL | ⚠️ 不推荐当前使用 | 功能强大但运维最重，属于过度设计 |

**一句话总结**：在这个项目当前的生命周期和规模下，SQLite 是最合适的选择。MySQL 和 PostgreSQL 是优秀的数据库，但它们带来的额外复杂度在这里无法换来实际收益。
